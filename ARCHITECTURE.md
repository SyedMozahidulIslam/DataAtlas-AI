# Architecture

## Current implementation

The local application is dependency-free so an evaluator can run the slice with Python 3.10+ and no network dependency installation. `dataatlas.server` uses Python's threaded HTTP server; `config.py` reads environment settings, `accounts.py` manages account/workspace/session operations, `security.py` hashes passwords and opaque browser tokens, `ingestion.py` validates CSV and infers a starting schema, `jobs.py` persists and runs idempotent ingestion jobs, `storage.py` atomically stores original Bronze files, `catalog.py` validates descriptive metadata and diffs schema versions, `profiling.py` computes column metrics, `sql_workspace.py` constructs isolated read-only query copies, `transformations.py` validates and executes linear operation recipes, `lineage.py` traverses persisted dataset edges, and `db.py` manages short-lived SQLite sessions and versioned migrations. The browser UI is plain HTML, CSS, and JavaScript served by that process. SQLite stores catalog/job/schema/query/transformation metadata, lineage events and edges, session token hashes, and bounded parsed dataset records as JSON text. Original CSV bytes are stored under the local lake directory. `DATAATLAS_HOME` selects the state directory.

### Current flow

Browser login/register → HTTP-only same-site session cookie → membership-resolved active workspace → multipart upload with idempotency key → persisted queued/running job and event timeline → bounded CSV validation → atomic immutable raw Bronze file write with SHA-256 → catalog rows/current schema + version/change records + lineage + succeeded job commit → catalog search/profile/schema/job-history reads scoped to the workspace. Job events record queue, start, completion, validation failure, execution failure, and restart recovery; elapsed duration and row counts are retained. A user can retry an eligible transient failure by uploading the exact same named file, bytes, and replacement target; each attempt has a new idempotency key and links to its parent. SQL workspace reads only those workspace datasets, copies them to a temporary in-memory SQLite database, applies an SQLite authorizer and resource limits, and returns a capped result. Query text and execution metadata are persisted to workspace-scoped history; result rows are not retained there. A saved transformation revision resolves one active-workspace source, validates its linear filter/select/derive steps against schema, runs them deterministically in process, and atomically registers a new Silver or Gold JSON-backed dataset with a transformation run, source lineage event, and persisted source-to-output edge. The lineage API traverses these edges only within the active workspace and enforces depth/node caps. Replacement writes a new Bronze object then moves the dataset metadata pointer inside a SQLite transaction; previous raw objects and schemas remain available. Validation errors are persisted as failed jobs. Startup marks any ingestion job interrupted while queued/running as failed and retryable.

Passwords use PBKDF2-HMAC-SHA256 with per-password random salts. Session cookies contain random opaque tokens; only SHA-256 digests are stored in the database. Sessions expire after 12 hours. Mutations reject mismatched `Origin` headers and cookies use `HttpOnly` and `SameSite=Strict`. Workspace membership is checked server-side for list, detail, profile, lineage, ingestion, and workspace selection. Dataset IDs are random UUID hex strings. Names are derived from sanitized source filenames and uniquified. Uploaded records remain strings or nulls; inferred types are metadata only, preserving source values.

Quality rules are validated against the target dataset schema and workspace. Each edit creates a rule-version snapshot; a run records its dataset schema version, rule version, execution status, evaluated rows, violation count, bounded samples, and duration. Enabled rules run after successful CSV ingestion/replacement and transformation execution; output-specific rules run when present, otherwise the source dataset's checks run after transformation. Users can also run them manually. Null, uniqueness, expected-type, numeric range/threshold, regex, allowed-value, row-count, and referential-integrity checks evaluate actual stored records. Failures create workspace-scoped alerts with read and acknowledgement timestamps. Ingestion, transformation, and schema-change failures also create alerts. No universal quality score is generated.

Ingestion is synchronous in the HTTP process for the current 10 MB/100,000-row learning limit. A per-workspace idempotency key is bound to the raw upload hash, filename, and optional replace target. A repeat with the same request returns the existing job result; key reuse with a different request returns a conflict. The local Bronze adapter validates opaque IDs, prevents paths escaping its data root, writes a temporary sibling file, and atomically places a versioned CSV. Catalog/profile queries still read parsed records stored in SQLite; the raw Bronze file is preserved for future analytical-engine adapters. The SQL workspace is separately bounded to 50 datasets, 100,000 rows, 25 MB of loaded record JSON, 10,000 SQL characters, 500 result rows, and a virtual-machine instruction budget. It permits read-only SELECT statements, restricts table reads to generated tables for the active workspace, and never opens the catalog database for user SQL. Transformation definitions support at most 25 steps, 200 output columns, 100,000 rows, and 25 MB of serialized output.

Schema versions are snapshots recorded on first ingestion and whenever the inferred schema changes. Change types cover added/removed columns, inferred type changes, nullability changes, and column ordering. Removal and type changes are classified as breaking; tightening nullability is breaking; nullable additions and order changes are informational. Rename is not inferred: ambiguous remove/add pairs remain separate events. Numeric outliers are counted using Tukey's 1.5×IQR fences; standard deviation is the population standard deviation. Quality scores are not synthesized.

## Target boundaries

The roadmap separates the UI, typed API, metadata database, analytical storage, query engine, ingestion/transform workers, and optional AI provider. The recommended mature stack is Next.js/TypeScript, FastAPI/Pydantic/SQLAlchemy/Alembic, PostgreSQL metadata, Parquet files, and DuckDB local analytics, with connector and storage interfaces. The first checkpoint intentionally avoids claiming those future components are already present.

## Security and limits

The server binds to loopback by default. A seeded demo account is intended only for local evaluation; change its password before sharing a deployment. There is no TLS, password reset, lockout/rate limiting, or account verification, so do not expose this server to untrusted networks. Upload size is capped to 10 MB and rows to 100,000; only UTF-8 CSV is accepted. SQLite parameter binding is used for values. Static file serving is constrained to the static directory. Raw uploaded content is never executed; user-authored SQL runs only in an isolated temporary database with an allowlisted read-only authorizer.
