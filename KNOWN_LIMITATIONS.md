# Known limitations

- Initial checkpoint supports CSV only (UTF-8, 10 MB, 100,000 data rows).
- SQLite stores analytical records as JSON text for this bounded demo; the SQL workspace makes temporary in-memory copies and does not persist analytical tables. Transformation outputs are stored as bounded JSON catalog records. There is no Parquet or DuckDB integration yet.
- Local username/password accounts, expiring sessions, workspace membership, and dataset workspace isolation are implemented. There is no password reset, account verification, rate limiting, fine-grained row/column authorization, or external identity provider. The default demo credential is public and the server binds to loopback; change the demo password before sharing and do not expose this local server to untrusted networks.
- Workspace invitations currently add an existing account by username through the API; there is no invitation UI or email flow. Existing legacy datasets are assigned to the seeded demo workspace during migration.
- Ingestion and transformation runs execute synchronously in the API process. Ingestion has a user-triggered retry for transient failures, bound to the original filename, bytes, and replacement target; validation failures are not retryable and retries stop after three attempts. There is no independent queue/worker, automatic backoff, schedule, cancellation, or transformation retry. The current transformation engine supports linear filter, project/select, and derive operations; it does not provide DAG editing, joins, or aggregation. A bounded read-only SQL workspace is available; it runs SELECT queries on temporary copies for up to 50 datasets, 100,000 rows, and 25 MB of loaded dataset records, with a 500-row result cap. It does not persist results, and query performance is not representative of DuckDB or a production analytics engine. Replaying a retry request uses the same idempotency key; a new retry gets a new key.
- Raw input is preserved as local CSV in the Bronze layer. It is not converted to Parquet and there is no DuckDB analytical engine yet. Parsed rows are also kept in SQLite JSON text for the current bounded local profile workflow.
- If the process exits between the atomic raw-file write and the SQLite catalog commit, an orphan raw file may remain. Running jobs are marked failed on restart; cleanup/reconciliation of orphan files is not implemented.
- The browser interface uses vanilla HTML/CSS/JavaScript rather than the planned Next.js/TypeScript stack; a hosted font is optional styling and the interface remains usable if it cannot load.
- Docker is not installed in the current environment, so no Compose-based PostgreSQL deployment is included or verified yet. The local SQLite mode remains the runnable default.
- CSV parser currently requires unique non-empty headers and rejects rows with extra cells. Ingestion reads the bounded upload into memory and does not provide incremental ingestion.
- Profile distinct counts hold values in memory and numeric range is presented only for numeric inferred columns.
- Catalog search is workspace-scoped but not paginated. Renames are not guessed; possible renames appear as separate add/remove changes.
- The lineage graph currently persists dataset-to-dataset edges for successful transformations. CSV ingestion is shown in each dataset's observed event history but is not yet a separate external-source graph node. The graph caps traversal at 200 nodes, 5,000 loaded edges, and eight levels; downstream schema-impact alerts are not implemented.
- Quality checks run against the bounded parsed records held in SQLite. Rules cover nulls, uniqueness, expected types, numeric thresholds/ranges, regexes, allowed values, row counts, and referential integrity. Custom SQL predicate rules are not supported. At most 20 failing row samples are retained per rule result. Alerts are in-app only; there is no email provider, staleness monitor, or downstream schema-impact analysis. A composite quality score is intentionally not calculated.
